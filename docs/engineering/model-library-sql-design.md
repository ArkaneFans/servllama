# SQL 驱动的本地模型库设计

状态：已实施并完成主机验证（2026-11-04）。实施前源码基线：ServLlama `485dea1`，mnn_engine `d83e3fa`。

## 1. 核心规则

模型库、数量、筛选及助手/服务器候选直接读取 `model_assets`。导入、下载和修改操作更新记录；旧内部 MNN 在启动时通过独立步骤扫描一次并登记。

列表刷新是纯查询：不扫描目录、不检查模型或 mmproj 文件、不读取配置或统计大小，也不修补记录、清理文件或自动改选投影器。文件不可用时，由用户实际加载或修改模型的操作报错。

删除遵守已确认的顺序：**内部模型先删文件（不存在则跳过），再删 SQL 行；外部模型只移除登记。** 语音模型采用相同规则，不写删除状态，不保留墓碑或自动续删。

沿用现有仓库、Provider、名称协调器和启动迁移。下载卡片、语音安装及任务运行仍由现有服务负责；本次不增加模型缓存、调度器或后台扫描。

## 2. 数据与身份

保持现有表、`UNIQUE(engine, path)` 和数据库 schema 1，补充信息放入 manifest。

| 信息 | 约定 |
| --- | --- |
| `id` | SQL 资产 ID，也是 `LibraryModel.id`；用于页面定位、更新、删除和助手引用，改名不变 |
| `runtime_id` / `name` | 引擎运行 ID / 显示名称；继续按已确认的规则同步名称 |
| `engine` / `storage_owner` | 引擎及文件归属；私有 GGUF 为 `app`，私有 MNN 为 `mnn_engine`，外部为 `external` |
| `path` | GGUF 文件路径或 MNN 目录路径 |
| GGUF manifest | 保留 `gguf` 详情，包括大小、时间、投影器和下载来源 |
| MNN manifest | 保存 `sizeBytes`、`importedAt`、`images`、`tools` 和 `warnings`，内部/外部共用同一映射 |

`LibraryModel.id` 直接复用 SQL ID，不再增加 `assetId`，也不再将 `mnn:<名称>` 等操作键作为列表身份。原生 MNN 的操作仍传 `runtimeId`；GGUF 文件操作所需的旧 `ModelDescriptor.id` 及 store 内部的关联方式保留，由仓库处理。页面和统一模型目录不解析 `libraryId` 前缀，旧 manifest 字段无需专门迁移或清除。

登记按引擎和路径复用已有行，更新保留其 ID 和无关 manifest 字段；改名按资产 ID 更新。删除后再添加属于新登记，不自动重新绑定历史。运行状态、端口和后端选择仍从运行时 Provider 获取。

语言模型登记使用 `ready`；语音保留原有安装状态，删除直接移除行。旧内部 MNN 缺少大小、时间或提示时使用 0、Unix epoch 和空列表，不访问文件补齐。

## 3. 读取与刷新

- `listLlmAssets()` 统一查询 `kind='llm' AND state='ready'`，供助手/聊天选择器及模型库共用。聊天保留供应商分组、搜索和名称排序；`listModels()` 使用同一批记录转换为 `LibraryModel`，沿用导入时间倒序。
- `listAssets()` 保留全部种类和状态，供语音等业务使用；助手/聊天使用 `listLlmAssets()`，不会展示旧的不可用语言模型登记。两者均为纯 SQL 查询。
- `LocalModelRepository.listModels()` 直接读取 `GgufModelStore`，移除模型/mmproj 存在性检查和自动清理。
- 保留 `ModelManagementProvider` 已有的 GGUF 详情集合与统一展示集合，以及串行刷新机制。两者都读 SQL，不为合并轻量查询增加返回类型或全局快照。
- 页面按稳定资产 ID 定位模型，去掉 MNN 改名后按名称找回模型的逻辑。加载继续复用现有查找和引擎入口；修改操作从 SQL 取得当前记录。

## 4. 操作闭环

| 操作 | 文件处理 | SQL 与刷新 |
| --- | --- | --- |
| GGUF 导入/下载 | 沿用现有复制或移动入库 | `GgufModelStore` 提交详情和资产，完成后刷新 |
| MNN 导入/下载 | 插件导入、校验并返回最终模型信息 | 统一仓库登记最终信息，成功后才通知完成 |
| 外部登记 | 只在登记时读取选定来源的必要元数据 | 保存真实路径、大小和能力，后续列表读保存值 |
| 内部改名 | 沿用目录改名，GGUF同步投影器路径 | 更新原行的名称、运行 ID 和路径，保留导入时间 |
| 外部改名 | 源文件不移动 | 更新原行的名称和运行 ID |
| 内部删除 | 删除模型目录、附属文件及 MNN 私有缓存；缺失则跳过 | 删除资产行并清除活动选择，随后刷新 |
| 外部移除 | 保留源文件；外部 MNN清理私有缓存 | 删除登记并清除活动选择，随后刷新 |
| 投影器修改 | 沿用明确的导入、选择、移除操作 | 更新原 GGUF manifest，列表不自动修补或改选 |

### 登记与名称

MNN 的 SAF 导入和下载共用一个登记方法，接收插件返回的 `MnnModelInfo`。保留现有流程：名称预留 → 插件导入及最终名称确认 → SQL 登记 → 释放预留并刷新。下载不能在登记失败时宣布完成。

名称协调器使用 SQL 已登记名称和现有内存预留，更新已有模型时按 SQL ID 排除自身。新导入的 MNN 在登记前尚无资产 ID，最终名称确认无需构造一个虚拟列表 ID；排除参数允许为空。原生导入和文件改名仍保留目标目录碰撞检查，防止覆盖未登记文件。

### 失败与刷新

导入、改名和 SQL 写入失败直接报告，沿用操作级即时补偿：新私有导入写库失败时尝试清理该目录，目录改名写库失败时尝试改回原名。补偿失败如实报告，不增加跨重启修复机制。文件操作与 SQL 无法保证进程异常退出时的原子性，本次接受这一限制。

模型 Provider 在每次提交后刷新自己的列表，并通过一个资产变更回调通知助手刷新；在现有 `AppProviderScope` 中连接，覆盖导入、下载、改名和删除。下载的现有 `onLibraryChanged` 走同一路径；改名/删除另外同步保存的运行选择，不再额外刷新一次助手。SQL 写入失败属于操作失败，页面刷新或可重建缓存清理失败只影响后续刷新/清理，不能撤销已经提交的修改。外部文件变化不触发自动更新能力、恢复登记或模型切换。

### 语言和语音模型删除

删除前保留现有的驻留、服务、导入/下载和活动任务检查，以及私有路径边界检查。通过后先删文件，再在 SQL 事务中删除模型行并清除活动模型选择；历史对话、Run 快照和已完成语音结果保留。

文件删除失败时不删记录；SQL 删除失败时保留记录并报错。用户重试仍走相同顺序，已不存在的文件自然跳过。`GgufModelStore.remove()` 实际删除行，引用清理按删除的资产 ID 执行，不先写 `missing`。

插件删除内部 MNN时根据合法私有目录删除文件和缓存，不依赖库存扫描或模型配置校验；模型目录缺失也要处理缓存。语音删除移除 `deleting` 写入和启动自动续删，已有带该值的旧记录仍可手动删除。删除不扩展空闲维护或文件清理队列。

## 5. Hive 迁移与一次性 MNN 登记

`LegacyImporter` 只负责 1.x 到 2.0 的 Hive 数据迁移，包括聊天、GGUF 详情和下载任务，沿用已有完成标记、事务与迁移界面。

旧内部 MNN 库存由 `UnifiedModelRepository.registerLegacyMnnInventory()` 独立登记。`main` 在 Hive 准入处理完毕后、业务 Provider 创建前调用它，使用独立的 `mnnSqlInventoryComplete` 标记。已经是 2.0 的用户直接在启动时补登记，不进入 Hive 迁移流程。

| 安装情况 | 本次处理 |
| --- | --- |
| 1.x 升级 | 先处理 Hive 迁移，再执行一次性 MNN 登记 |
| 已完成 Hive 迁移的 2.0 | 启动时只补登记旧 MNN |
| 没有 Hive、只有旧 MNN | 启动时正常登记，不依赖 Hive 文件或标记 |
| 新安装 | 库存为空，提交 MNN 完成标记 |
| MNN 标记已完成 | 仅查标记，不再扫描旧库存 |
| 用户选择跳过 Hive 迁移 | 只跳过 Hive 数据，仍执行 MNN 登记 |

通过插件的 `listImportedModels()` 在事务外读取私有库存，随后在一个 SQL 事务内登记元数据并写完成标记。复用导入/下载的登记方法，已有内部行保留 UUID 并补齐元数据；旧 `missing` 行不恢复，外部路径不接管，未扫描到的记录不删除。

Hive 与 MNN 分别提交。MNN 读取或写入失败时不标完成，也不撤销已经成功的 Hive 迁移；沿用普通启动失败的重试入口，下次只重试未完成步骤。MNN 登记不读 Hive、不控制 Hive 的跳过或完成状态，也不增加迁移页面、登记队列或恢复机制。

扫描不调用 `initialize()`、加载权重或启动 HTTP/前台服务。完成登记后的普通启动、模型列表刷新和助手恢复只读 SQL。

### 旧软删除记录清理

旧 MNN 登记之后，启动单独执行 `cleanupLegacyMissingModels()`：在一个 SQL 事务内物理删除 `kind='llm' AND state='missing'` 的旧行、清除这些资产的当前助手引用，并写入 `legacyMissingLlmAssetsRemoved` 完成标记。空库存也标完成，失败不标完成，沿用启动重试；已有 MNN 登记和 Hive 迁移标记不受影响。

先登记再清理，避免旧 `missing` 行被删后，其残留 MNN 目录又被当作新模型登记。清理只操作 SQL，保留模型文件、语音资产及历史快照，不增加文件扫描、清理队列或新页面。聊天查询本身只返回 `ready` 记录，清理前后都不会显示这些旧灰色条目。


## 6. 实施范围

| 模块 | 改动 |
| --- | --- |
| 统一仓库、GGUF 仓库及 store | 纯 SQL 查询、MNN 登记、按资产 ID 修改和实际删除行 |
| `LibraryModel`、模型页及 Provider | 使用稳定 SQL ID，去掉前缀解析和按名称重新定位；保留现有展示集合 |
| 下载、助手、名称协调器及 `AppProviderScope` | 登记后完成操作、共用提交后刷新回调，SQL 名称检查，去掉库存 reconciliation 状态 |
| `main` 与统一仓库 | 共用语言模型查询；独立的一次性 MNN 登记与旧软删除 SQL 清理，Hive 保持原有流程 |
| 模型引用清理 | 删除事务清除活动选择，保留历史 |
| 语音服务、插件 Kotlin 模型仓库 | 简化删除，缺文件可删除登记，移除自动续删 |

MNN 插件的独立扫描接口仍供其他消费者和诊断页使用，C++ 推理和原生库不变。已同步更新 [冷启动](cold-start.md)、[外部模型](external-models.md)、[语音](speech.md) 和插件 README。

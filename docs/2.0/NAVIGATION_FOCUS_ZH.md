# 导航与输入焦点

2026-10-03，`2.0.0-dev.25+39`。

## 交互规则

- 离开当前页面时释放原输入焦点。返回后保留草稿、表单值与搜索条件，键盘保持关闭，用户再次点击输入框才开始输入。
- 打开对话框、底部弹窗、操作菜单遵循同一规则。目的界面明确设置了自动聚焦的输入框仍可正常唤起键盘，例如添加模型、重命名或编辑消息。
- 侧边栏展开时释放聊天焦点，收起时释放侧边栏搜索焦点。点击功能入口仍直接打开页面，返回后侧边栏保持展开。
- 标签页实际切换时释放焦点，覆盖点击、滑动和控制器切换；再次点击当前标签不会中断编辑。
- 正常编辑、文本选择、主题更新，以及被阻止的页面返回，不触发全局清焦点。修改后台路由但没有切换当前页面，也不打断输入。

## 实现

Flutter 的路由焦点作用域会记住之前聚焦的控件。只隐藏软键盘，或只对外围 `FocusScope` 调用 `unfocus`，可能仍留下内部输入框的焦点记忆。

应用使用一个 `AppNavigationObserver`，取代原来只处理消息提示的观察器。在 `didChangeTop` 中统一关闭临时提示，并对属于离开路由的当前焦点调用 `unfocus()`。这会清除输入框所在作用域的焦点历史。没有在返回时重新创建页面、清空输入，也没有追加延时操作；因此新界面的主动聚焦不会被晚到的全局回调取消。

不经过 Navigator 的两类应用内切换由共享组件处理：`AppTabBar` 监听实际标签索引变化，`PushSidebar` 监听展开/收起状态。发现模型页原有的重复监听已移除，UI 原语页面复用同一标签组件；助手的页内能力标签也释放当前输入焦点。模型重命名、搜索提交等原有清焦点位置改为释放当前焦点，避免仅清外围作用域。

Android 图片/文件选择器是系统界面，不产生 Flutter 路由事件。聊天添加图片、语音选择音频在调用选择器前主动释放焦点。头像选择已有底部弹窗，先由全局路由规则清理焦点。没有把焦点逻辑放进模型、数据库或文件服务层。

参考依据：Kelivo 的聊天输入和交互控制中有主动 `unfocus` 处理；RikkaHub 的 `ChatPage.kt` 在抽屉展开时调用 `clearFocus(force = true)` 与键盘隐藏。它们的具体实现不同，本次依据 ServLlama 的 Flutter 导航结构统一行为。

## 验收步骤

1. 聊天输入一段草稿并保持键盘打开，展开侧边栏：键盘关闭。分别进入助手、服务器、模型库、语音和设置后返回，草稿仍在，输入框不自动聚焦。
2. 点击侧边栏搜索框，再进入设置后返回：侧边栏仍展开，搜索框不自动唤起键盘。再次输入后收起侧边栏，键盘也应关闭。
3. 聊天输入草稿，打开模型选择：原键盘关闭。点击弹窗搜索框后关闭弹窗，聊天草稿保留，键盘关闭。重新点击聊天输入框可继续输入。
4. 供应商添加模型、会话重命名、编辑消息等弹窗中的自动聚焦正常；关闭弹窗后不把焦点还给原输入框。检查点击遮罩与系统返回两种关闭方式。
5. 在模型库搜索、语音文本框中输入，点击或滑动切换标签再切回：文本保留，键盘不自动弹出。再次点击当前标签不打断输入。
6. 点击聊天“+”或语音音频导入后取消系统选择器，返回后键盘保持关闭。
